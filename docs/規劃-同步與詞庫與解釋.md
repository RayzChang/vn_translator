# 台越翻譯機 — 同步、詞庫與解釋功能規劃

## 一、現況與目標

- **現況**：API 金鑰、設定、翻譯紀錄都存在各裝置的 localStorage，**不會跨裝置同步**。
- **情境**：上班用公司電腦、下班用家裡電腦或手機，希望**同一帳號下**設定與資料一致。
- **延伸需求**：
  1. **多裝置同步**：金鑰、設定、必要時翻譯紀錄或詞庫可跨裝置一致。
  2. **自建詞庫／資料庫**：存常用用語、自訂譯法，**先查詞庫再打 API**，省費且加快。
  3. **翻譯後解釋**：翻譯結果下方多一個「解釋」區塊，包含單字拆解、文法結構、縮寫／網路用語說明。
  4. **寫入詞庫時去重**：存入前檢查是否已存在，避免重複儲存。

以下依「同步」「詞庫／資料庫」「解釋」「去重」分項規劃，最後給實作階段建議。

---

## 二、多裝置同步

### 2.1 為什麼需要後端

- 同步 = 把「目前裝置的資料」存到「一個大家都能讀寫的地方」。
- 那個地方只能是**你自己控制的後端 + 資料庫**（或受信任的 B2C 服務），不能只靠 localStorage。

### 2.2 要同步什麼

| 項目 | 說明 | 優先 |
|------|------|------|
| API 金鑰 | 加密後存後端，各裝置登入後拉取 | 高 |
| 設定 | 模型、深色模式、預設選項等 | 高 |
| 自建詞庫 | 你新增的詞條（見下一節） | 高 |
| 翻譯紀錄 | 可選：只存最近 N 筆，方便多裝置延續閱讀 | 中 |

### 2.3 身分識別（誰的資料）

- **方案 A**：簡易「裝置代碼 + 密碼」  
  - 第一次使用設一組密碼，後端用「帳號 = 裝置代碼或自訂 ID + 密碼」辨識。  
  - 優點：實作快、不必接第三方登入。  
  - 缺點：要自己記一組密碼、換裝置要重新綁定或輸入同一組。
- **方案 B**：用 Google / GitHub 等 OAuth 登入  
  - 優點：一帳號多裝置，體驗好。  
  - 缺點：要接 OAuth、後端要存 token/使用者 ID。
- **建議**：若只有你（與家人）使用，可先做**方案 A**；之後若要分享給多人再考慮方案 B。

### 2.4 金鑰安全

- API 金鑰在後端**必須加密儲存**（例如用 AES，金鑰由「使用者密碼」或環境變數衍伸）。
- 傳輸一律 **HTTPS**；前端只把「加密後的金鑰」或「代號」送後端，後端再解密後代為呼叫 Gemini（即**代理呼叫**），前端不直接拿明文金鑰打 API。

## 三、詞庫／資料庫設計

### 3.1 詞庫要存什麼

- **詞條**：例如「原文」↔「譯文」+ 備註（可選）。
- **方向**：越→中、中→越分開存，或同一筆用「語向」欄位區分。
- **來源**：  
  - 你手動新增的「自訂用語」。  
  - 可選：翻譯結果經你確認後「加入詞庫」（寫入前做去重，見第五節）。

### 3.2 資料表概念（先規劃，實作時可微調）

```text
詞彙表 (vocabulary)
- id (主鍵)
- user_id (若有多人，區分誰的)
- direction: 'vn2zh' | 'zh2vn'
- source_text: 原文（例如越南文或中文）
- target_text: 譯文
- note: 備註（可選）
- created_at
- updated_at

唯一約束 (防重複): (user_id, direction, source_text)
或  (user_id, direction, LOWER(TRIM(source_text)))
```

- 查詢時：先依 `user_id`、`direction`、`source_text`（或正規化後）查詞庫；**有命中就先回傳詞庫結果，不呼叫 API**；沒命中再打 API，並可選擇是否「加入詞庫」（再走去重邏輯）。

### 3.3 翻譯快取（可選）

- 若希望「同一句不重複打 API」，可另設**翻譯快取表**：  
  - 欄位：`input_hash`（原文雜湊）、`direction`、`model_id`（可選）、`output`、`created_at`。  
- 查詢前先算 `input_hash`，有就回快取；沒有再打 API 並寫入快取。  
- 與「詞庫」差別：詞庫是你**刻意保留的用語**；快取是**任何翻譯結果的暫存**，可設 TTL 或筆數上限。

### 3.4 省費與速度

- **先查詞庫**：命中 → 直接回傳，不呼叫 API → 省費、延遲低。  
- **再查快取（若實作）**：命中 → 直接回傳 → 省費、延遲低。  
- **最後才呼叫 API**：未命中再打 Gemini，並可選擇是否寫入詞庫／快取。

## 四、翻譯結果 + 「解釋」區塊

### 4.1 需求整理

你希望翻譯下方多一個區塊，AI 幫忙：

1. **單字／詞拆解**  
   - 例：「xin chào」→ 最普遍的打招呼；xin 的意思為…；chào 的意思為…。
2. **文法結構**  
   - 這句越南語的組成、語序、文法重點。
3. **縮寫／網路用語**  
   - 例：iu = yêu 等，並標註是網路或口語用法。

### 4.2 實作方式（不改 DB 也能先做）

- **呼叫一次 API**：在現有「翻譯」的 system + user prompt 裡，**一次要求**模型輸出兩部分：  
  - **翻譯**（維持現在格式）。  
  - **解釋**：單字拆解、文法、縮寫／網路用語（若無則省略）。  
- 回傳格式可約定為：  
  - 例如用「---」或 JSON 分開「翻譯」與「解釋」，前端再拆成兩個區塊顯示；  
  - 或要求模型用固定標題輸出，例如「【翻譯】… 【解釋】…」，前端用簡單解析切開。

這樣**不必先建資料庫**就能有「翻譯 + 解釋」；之後若把「解釋」也存進 DB，再考慮欄位即可。

### 4.3 與詞庫的配合

- 若**有詞庫命中**：可只顯示「詞庫譯文」+ 可選的「詞庫備註」；若也要「解釋」，可選擇再打一次 API 只求解釋（或日後在詞庫多存「解釋」欄位，一次存好）。  
- 若**走 API 翻譯**：一次回傳「翻譯 + 解釋」，前端兩塊都顯示；若要「加入詞庫」，只存原文＋譯文（＋備註），解釋可選存。

## 五、寫入詞庫時的去重

### 5.1 何時寫入

- 使用者手動「加入詞庫」：翻譯結果下方按鈕。  
- 或（可選）後台「從歷史紀錄加入詞庫」。

### 5.2 去重規則

- **同一使用者、同一語向、同一原文**視為同一筆。  
- 實作方式：  
  - **唯一約束**：DB 設 `UNIQUE(user_id, direction, source_text)`，`source_text` 建議先做 `TRIM`、可選 `LOWER` 或正規化空白。  
  - 寫入前先 **SELECT** 是否存在；若存在則 **UPDATE** 譯文／備註，或直接回傳「已存在，未重複新增」。  
  - 若用唯一約束，則 **INSERT** 時用 `ON CONFLICT (user_id, direction, source_text) DO UPDATE SET ...`（PostgreSQL）或等效語法，避免重複列。

### 5.3 前端顯示

- 若選擇「已存在則更新」：可提示「已更新詞庫中的譯文」。  
- 若選擇「已存在就不寫入」：可提示「該詞已存在於詞庫，未重複儲存」。

## 六、系統架構示意（規劃用）

```text
[ 手機 / 公司電腦 / 家裡電腦 ]
         │
         │ HTTPS
         ▼
[ 你的後端 API ]
  - 登入／同步設定（含加密金鑰）
  - 詞庫 CRUD、查詢、去重寫入
  - 翻譯代理（後端用使用者金鑰呼叫 Gemini）
  - 可選：翻譯快取
         │
         ├── [ 資料庫 ]
         │     - 使用者／設定／詞彙表／可選快取表
         │
         └── [ Google Gemini API ]
                - 翻譯 + 解釋（一次或分兩次呼叫）
```

- 前端：仍為 PWA；登入後從後端拉設定與詞庫；翻譯請求改為「打你的後端」，由後端查詞庫／快取再決定是否打 Gemini。

## 七、實作階段建議

| 階段 | 內容 | 說明 |
|------|------|------|
| **Phase 1** | 翻譯 + 解釋（不接後端） | 調整 prompt，一次要翻譯 + 單字/文法/縮寫解釋；前端多一個「解釋」區塊。不需 DB，先滿足「學習用」需求。 |
| **Phase 2** | 後端 + 簡易帳號 + 同步 | 建一個小後端（如 Vercel Serverless + 資料庫）；簡易註冊/登入；同步 API 金鑰（加密）與設定；前端改為呼叫後端代理翻譯。 |
| **Phase 3** | 詞庫 CRUD + 去重 | 詞彙表建立；翻譯前先查詞庫；「加入詞庫」按鈕 + 寫入前去重（唯一約束 + INSERT/UPDATE 邏輯）。 |
| **Phase 4** | 可選：翻譯快取、歷史同步 | 依需求加快取表、歷史紀錄同步；可與詞庫共用同一 DB。 |

建議先做 **Phase 1**（解釋區塊），立刻有體感；再依時間決定是否接 **Phase 2～3**（同步 + 詞庫）。

---

## 八、技術選型建議（供後續實作參考）

- **後端**：Vercel Serverless Functions（與你現有部署一致）或 小型 Node（Express/Fastify）服務。  
- **資料庫**：  
  - Vercel Postgres / Supabase / PlanetScale 等（有免費額度，支援唯一約束與索引）。  
  - 若自架：PostgreSQL 或 SQLite（單機）皆可。  
- **金鑰加密**：Node 內建 `crypto`（AES-256-GCM），金鑰由使用者密碼或環境變數衍伸。  
- **前端**：現有 React PWA 不變，新增「登入／同步狀態」「解釋區塊」「加入詞庫」等 UI。

若你願意，下一步可以從 **Phase 1（翻譯 + 解釋區塊）** 開始，直接改現有前端的 prompt 與畫面；完成後再規劃 Phase 2 的 API 與 DB schema 細部設計。
